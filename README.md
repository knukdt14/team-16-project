# 전기차 구매보조금 상담 AI 서비스

KDT 14기 웹 프로젝트 6팀 (team-16-project)

2026년 전기자동차 보급사업 보조금 업무처리지침(RAG)과 전국 지자체 차종별 보조금 데이터(CSV)를 결합한 상담 챗봇입니다.

> **핵심 설계**: 금액은 LLM이 생성하지 않습니다. CSV 조회값만 사용하고, RAG는 "왜 그 금액인지"를 설명합니다.

---

## 프로젝트 개요

전기차 보조금은 **같은 차라도 지역과 트림에 따라 금액이 다릅니다.** 경기도 EV6만 해도 시·군에 따라 651만원에서 976만원까지 차이가 납니다.

| 질문 유형 | 예시 | 처리 방식 |
|---|---|---|
| 금액 | "성남시에서 EV6 사면 얼마?" | CSV 정확 조회 |
| 규정·자격 | "청년이 첫 차로 사면 더 주나요?" | 지침 문서 RAG |

## 주요 기능

### 정확한 금액 조회

전국 159개 시·군·구 × 121개 모델의 국비/지방비/전환지원금 조회.

```
입력: 부산 / 더뉴EV6 스탠다드
출력: 국비 501만원 + 지방비 180만원 = 681만원
```

### 되묻기 (Clarifying Question)

정보가 부족하면 **답을 만들어내지 않고 되묻습니다.** LLM을 호출하지 않으므로 응답이 즉시(0.1초 이내) 반환됩니다.

```
Q. "경기도에서 EV6 사려는데 얼마예요?"
A. 경기 기준 651~976만원 범위입니다.
   시·군·구마다 지방비가 달라 정확한 지역을 알려주시면 확인해드릴게요.

Q. "광주에서 EV6 얼마예요?"
A. '광주'에 해당하는 지역이 여러 곳입니다. (광주광역시 / 경기 광주시)
```

평균을 내지 않습니다. 경기도 평균 730만원은 어느 시·군에도 존재하지 않는 금액이기 때문입니다.

### 규정 기반 상담

업무처리지침 66개 청크를 검색해 근거와 함께 구조화된 형식으로 답변합니다.

```
**국비 지원액의 20%가 추가 지원됩니다**

- 대상: 19세 이상 34세 이하 청년 (「청년기본법」 기준)
- 조건: 개인이 생애 첫 자동차로 전기차 구매 시

(근거: 4-1-2 중·대형, 소형)
```

### 추가지원금 계산

지침의 계산 순서를 코드로 구현. 비율 지원을 먼저 적용하고 정액(다자녀)을 마지막에 더합니다.

```
차상위 + 3자녀, 국비 500만원
→ 500 + (500 × 20%) + 200 = 800만원   ✓ 지침 계산 예시와 일치
```

## 시스템 구조

```
┌───────────┐   HTTP    ┌───────────┐  import   ┌───────────┐
│ Frontend  │ ────────▶ │  Backend  │ ────────▶ │ AI Engine │
│ Streamlit │ ◀──────── │  FastAPI  │ ◀──────── │  RAG/LLM  │
└───────────┘   JSON    └───────────┘           └─────┬─────┘
                                  ┌───────────────────┼───────────────┐
                                  ▼                   ▼               ▼
                            ┌──────────┐      ┌──────────┐    ┌──────────────┐
                            │  Chroma  │      │   CSV    │    │ Upstage Solar│
                            │ 지침 RAG │      │ 금액 조회│    │  (폴백: HF)  │
                            └──────────┘      └──────────┘    └──────────────┘
```

프론트엔드는 AI 엔진을 직접 import하지 않고 HTTP로만 통신합니다. 이 경계 덕분에 Docker 컨테이너 분리가 가능합니다.

### 질의 처리 흐름

```
질문
 ├─ extract()   지역·모델·트림·자격조건 추출 (규칙 기반)
 ├─ classify()  금액 질문 / 규정 질문 판별
 ├─ lookup()    CSV 조회 ─┬─ 모호함 → 되묻기 후 종료 (LLM 미호출)
 │                        └─ 확정 → 금액 확보
 ├─ search()    벡터 검색
 └─ generate()  LLM 답변 생성 (금액은 조회값 그대로 삽입)
```

## 설계 결정 기록

### 1. pypdf → pdfplumber 교체

pypdf로 추출하면 한국어 공백이 **전부** 사라집니다.

```
pypdf      : '보급사업참여업체가기후부및한국환경공단의시정또는...'
pdfplumber : '보급사업 참여 업체가 기후부 및 한국환경공단의 시정 또는...'
```

공백이 없으면 형태소 분석이 불가능해 BM25가 작동하지 않습니다.

### 2. 정규식 앵커 누락으로 인한 30페이지 유실

별표 제외 패턴을 `\[별표\s*1\]`로 작성했는데, 본문 중 "산출방식은 **별표 1**과 같음" 문구에 매칭되어 제외 모드가 켜졌습니다. 그 결과 p.14~46이 통째로 누락됐습니다.

에러도 나지 않고 청크도 생성되어 정상으로 보였으나, **있어야 할 내용을 검증**해 발견했습니다.

```python
must_have = ["거주기간", "의무운행", "회수요율", "전기화물"]
for k in must_have:
    assert any(k in c["text"] for c in chunks), f"누락: {k}"
```

| | 수정 전 | 수정 후 |
|---|---|---|
| 청크 수 | 56 | 122 |
| 거주기간 | 0건 | 1건 |
| 전기화물 | 0건 | 11건 |

### 3. 청크 병합 — 검색 성능 26% 개선

`○` 단위로만 자르면 한 조항이 지나치게 잘게 쪼개져(중앙값 165자, 200자 미만이 122개 중 77개) 정답 정보가 여러 청크로 흩어집니다.

같은 섹션 내 인접 청크를 300~900자 범위로 병합했습니다.

| | 병합 전 | 병합 후 |
|---|---|---|
| 청크 수 | 122 | 66 |
| 중앙 길이 | 165자 | 362자 |
| **Dense Hit@5** | 0.54 | **0.68** (+26%) |
| **Dense MRR** | 0.456 | **0.502** (+10%) |

**모델이나 검색 방식이 아니라 청킹 단위가 성능을 좌우했습니다.**

단, 각주(`*`, `※`, `-`)는 반드시 본문과 같은 청크에 유지했습니다. 계산 예시가 각주에 있어 분리하면 계산 질문에 답할 수 없습니다.

### 4. 금액을 RAG로 처리하지 않은 이유

LLM은 숫자를 자신 있게 지어냅니다. 이 도메인에서 금액 오류는 사용자의 실질적 금전 손실로 이어집니다.

금액은 CSV 조회 결과를 프롬프트에 주입하고, 시스템 프롬프트에서 숫자 생성을 명시적으로 금지했습니다. **이 설계 덕분에 LLM이 규정을 잘못 해석하는 경우에도 금액 자체는 틀리지 않습니다.**

### 5. 평균 대신 범위 + 되묻기

경기도 EV6는 651~976만원입니다. 평균 730만원은 어느 시·군에도 존재하지 않습니다. 사용자가 이를 믿고 대리점에 가면 최대 79만원의 오차가 발생합니다.

정보가 부족하면 **LLM을 호출하지 않고 즉시 되묻습니다.**

### 6. 엔티티 추출을 LLM이 아닌 규칙 기반으로

지역 159개, 모델 121개가 모두 CSV에 있어 후보가 유한합니다.

- **정확도**: LLM은 "경기 광주"를 "광주광역시"로 바꿀 수 있으나, 규칙 기반은 목록에 없으면 잡지 않습니다
- **안전성**: LLM이 임의로 하나를 고르면 되묻기 안전장치가 무력화됩니다
- **속도**: LLM 호출이 2회로 늘어 응답 시간이 배가됩니다

제조사명 접두어(`기아 EV` → `EV` + 제조사 필터)를 분리해 매칭 실패를 줄였습니다.

### 7. 하이브리드 검색 미채택

Dense + BM25를 RRF로 결합했으나 **Dense 단독보다 성능이 낮았습니다.** 가중치 스윕 결과 BM25 비중이 커질수록 단조 감소했습니다.

| w_dense | w_bm25 | Hit@5 | MRR |
|---|---|---|---|
| **1.00** | 0.00 | **0.68** | **0.5020** |
| 0.90 | 0.10 | 0.66 | 0.4953 |
| 0.70 | 0.30 | 0.62 | 0.4487 |
| 0.00 | 1.00 | 0.42 | 0.2890 |

단, 평가셋이 원문 표현을 의도적으로 회피해 작성되어 **BM25가 강점을 갖는 정확 매칭 질의(조항번호, 트림명 등)가 포함되지 않았습니다.** BM25가 무용한 것이 아니라 현 평가셋의 질의 유형에서 기여하지 못한 것으로 해석해야 합니다.

### 8. LLM 프로바이더 전환 + 폴백 구조

로컬 3B 모델은 CPU에서 답변당 70~170초가 걸리고, 여러 차종 규정이 섞인 문서에서 조항을 혼동했습니다. 프롬프트로 개선을 시도했으나 3건 해소에 1건 신규 발생하는 양상이 반복되어 모델 한계로 판단했습니다.

Upstage Solar로 전환하되, **키가 없어도 동작하도록** 폴백을 넣었습니다.

```
LLM_PROVIDER=auto
  키 있음 → Upstage Solar
  키 없음 → HuggingFace 로컬

Upstage 실패(인증·토큰소진·타임아웃·응답없음)
  → HuggingFace 자동 전환, 서비스 중단 없음
```

채점자가 clone 후 `docker compose up` 만으로 실행할 수 있어야 하므로 폴백은 필수 요건입니다. 폴백 모델은 지연 로딩하여 Upstage 사용 시 6GB 다운로드를 피합니다.

**추론 모델 대응** — `solar-pro4`는 사고 토큰을 먼저 소비한 뒤 답변을 생성합니다. `max_tokens`가 부족하면 사고 도중 잘려 `content`가 `None`이 되므로 Upstage 전용 토큰 상한을 분리했습니다(기본 8000).

### 9. 답변 형식 구조화

"3~4문장으로"처럼 추상적으로 지시하면 모델이 잘 지키지 않습니다. **마크다운 틀을 프롬프트에 직접 그리고 완성 예시를 1개 넣자** 형식 준수율이 크게 올랐습니다.

조건부 지원금 합산 문제도 함께 해결했습니다. 전환지원금은 노후 내연기관차 교체 시에만 지급되는데, 기본 지원액에 합산하면 실제보다 130만원 큰 금액으로 오인됩니다.

| | 개선 전 | 개선 후 |
|---|---|---|
| 평균 분량 | 6~10줄 / 300자+ | **4.3줄 / 160자** |
| 형식 일관성 | 매번 다름 | 10/10 준수 |
| 조건부 금액 | 기본액에 합산 | 불릿 분리 |
| 근거 표기 | "문서 1~4" | 조항번호 |

## 품질 검증

정량(검색)과 정성(답변) 두 축으로 나누어 검증했습니다. **수치로 잡히는 문제와 사람이 읽어야 잡히는 문제가 다르기 때문**입니다.

### 검색 성능 (정량)

`eval/questions.csv` 50문항 + `eval/references.csv` 정답 청크 라벨.

**평가셋 작성 원칙**: 문서 원문 표현을 의도적으로 회피했습니다. 원문을 그대로 베끼면 BM25가 단어를 직접 매칭해 지표가 부풀려지고, 실제 사용자 질의와 괴리가 생깁니다.

| 문서 표현 | 평가셋 질문 |
|---|---|
| "거주기간 요건 기준은 3개월 이내" | "이사 온 지 얼마 안 됐는데 신청 가능한가요?" |
| "차상위 이하 계층" | "형편이 어려운 사람한테 주는 혜택도 있어요?" |

**결과 (top-5, 50문항)**

| 방식 | Hit@5 | MRR | Recall@5 |
|---|---|---|---|
| **dense** | **0.68** | **0.502** | **0.64** |
| bm25 | 0.42 | 0.289 | 0.39 |
| hybrid (0.7:0.3) | 0.62 | 0.449 | 0.58 |

실패 16문항을 전수 검토한 결과 **정답 라벨 오류는 없었고 전부 실제 검색 실패**였습니다. 공통 패턴은 질문이 일상어인데 문서가 행정 용어인 경우입니다.

| 질문 | 문서 표현 |
|---|---|
| "중간에 팔면 돈을 토해내야 하나요?" | "의무운행기간이 경과하지 않은 경우 보조금을 회수" |
| "누가 신청할 수 있나요? 회사도 되나요?" | "개인, 법인, 개인사업자, 공공기관..." |

### 답변 품질 (정성)

`check_answers.py` 로 10개 질의를 실행해 육안 점검했습니다. 검색 지표가 좋아도 최종 답변에는 별도의 오류가 존재합니다.

**로컬 3B에서 발견된 오류 4종**

| 문항 | 오류 |
|---|---|
| Q6 거주요건 | "3개월 **이내**라 신청 가능" (실제는 3개월 이상 필요) |
| Q7 재지원제한 | "중복 지원 가능" (실제는 최초 1대만) |
| Q8 가격구간 | "보조금의 50%인 3천만원" (계산 대상 오인) |
| Q9 차상위+다자녀 | 화물차 기준 30% 적용 (승용은 20%) |

**모델별 비교**

| | 3B (로컬) | Solar Pro 2 | Solar Pro 4 |
|---|---|---|---|
| 평균 분량 | 45줄 | 4.3줄 | 4.3줄 |

| 조건 반전 오류 | ❌ | ✅ | ✅ |

Q6은 지침 원문이 "지자체가 정하되 3개월을 넘기지 말 것"이라는 구조인데, Solar Pro 4만 이 뉘앙스를 정확히 옮겼습니다.

### 시행착오 기록

**추론 모델의 사고 토큰** — `max_tokens=250` 으로 호출했더니 사고 과정이 한도를 다 써서 `content`가 비었습니다. 응답은 200 OK였으나 `content: null` 이라 예외가 발생했습니다.

**reasoning 필드 오용** — `content` 가 비면 `reasoning` 을 대신 반환하도록 구현했으나, 이는 모델의 내부 사고 과정이라 "Thinking Process: 1. Analyze the Request..." 하는 영문 독백이 그대로 노출됐습니다(평균 45줄/3570자). 해당 폴백을 제거하고 토큰 상한을 조정해 해결했습니다.

**최신 모델이 항상 최선은 아님** — Solar Pro 4는 추론 모델이라 문서 요약 작업에는 과할 수 있습니다. 정확도는 가장 높았으나 응답 시간이 Pro 2 대비 5~30배입니다. 작업 성격에 맞는 모델 선택이 최신 모델 사용보다 중요합니다.
